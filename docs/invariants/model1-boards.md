# Model 1 boards on an original Model 2 (board-level: `model1io.h`, `model1_sound.h`, `z80.h`)

Part of m2-hle2's load-bearing invariants, indexed in [CLAUDE.md](../../CLAUDE.md): facts reverse-engineered or debugged into the emulator, in no datasheet. Do not re-derive them.

Daytona USA (`profiles/daytona.h`, Pinboard #1035) is MAME's model2o: an i960 CPU board with an MB86234 TGP (`tgp.h`, as Sega Rally's), and two boards Sega carried over from Model 1, the I/O board and the sound board. Any model2o set that names them gets them through `quirks.model1_io` and `quirks.model1_sound`.

- **A byte or halfword store to the TGP's ports pushes a whole word** (`model2a.h`, `model2a_copro_write_cb`): the value in its byte lane, zeros around it, at the word address. MAME's 32-bit handlers take the shifted bus word and ignore the mask. Daytona sends some TGP arguments with `stos`; the old `size != 4` return dropped them, so the FIFO was short of arguments and the TGP's results were out of step. Sega Rally makes no such store: its det_digest is identical either way (3000 frames).
- **The I/O board's Z80 runs only when the CPU board touches its dual-port RAM**, caught up to board time one instruction at a time (375 board units per T-state at 4 MHz). What the i960 reads therefore depends on board time alone, which keeps netplay and savestates exact. Its 93C46 runs on the Z80's clock while the Z80 runs (`g_eeprom_clock_fn`), not the CPU board's. A gap longer than four frames is skipped, not run (ten seconds on the Advanced board, below). `model1io.h`'s header has the Z80 map, the 315-5338A's registers and the ports.
- **The Z80 core is checked by ZEXDOC and ZEXALL** (all OK). `tests/z80_test.c` (a ctest) keeps a short check; keep the undocumented flags (XF/YF, MEMPTR) when changing `z80.h`.
- **The sound board is MAME's segam1audio**, not the SCSP board (`model1_sound.h`, run by `sound_run_m1` in `sound.h`). It has a 10 MHz 68000, an i8251 whose RxRDY is the 68000's level-2 interrupt, two MultiPCMs and a YM3438. The i960's serial bytes reach the board's i8251 over the same timed line as the SCSP's MIDI port (`sound_uart_t`; at the model2o clock that is 705.6 units per clock, 7056 per µs). What the 68000 sends goes back to the i960's receiver (MAME `rxd_handler`). The 68000 map is in the header. Note the mirror: the upper ROM socket's 128 KB appears again at 0x80000.
- **The MultiPCMs make 44.1 kHz samples, not their own 44642.857** (10 MHz / 224). The pitch steps are built at the chip's rate and divided by 44100. The envelope and level rates are scaled by chip/out, and the LFO steps use 44100. So voices play at MAME's speed on m2-hle2's one audio grid. The tables use host `pow()`: they feed the output only, and nothing on the board reads it.
- **Only the YM3438's timers and busy flag are emulated.** The driver keeps tempo by polling the timer flags, so they must be exact (ymfm: A = (1024 - TA) x 144 clocks, B = 16 x (256 - TB) x 144; busy 192 clocks after a data write; YM clock = 68000 clock x 4/5). Daytona never keys an FM voice: in 60 s of MAME attract and a race, register 0x28 was written 12 times, all key-offs. A key-on is logged at WARN; if another set keys one on, FM is the next thing to write.
- **Held against MAME** (`-wavwrite`, 40 s of attract): the per-second peaks and RMS have the same shape, and clipping is as rare (306 vs 1054 samples of 3.5 M at |x| >= 16300). Our music starts about 4 s earlier than MAME's, in line with the board booting faster than MAME's (open).
- Daytona is a new profile, so its sound board needed no `NETPLAY_PROTO_REV` bump. Every other profile runs the SCSP board exactly as before (`sound_select_board(false)`): the ctest det digests are unchanged.
- **Virtua Cop (`profiles/vcop.h`, Pinboard #1286) has the Advanced Model 1 I/O board** (MAME `model1io2`, `quirks.model1_io2`, `model1io_install_advanced`), the same CPU board (`board/model2o.h`, shared with Daytona) and the same sound board. Its program is epr-17181.6 in `model1io2.zip`, the profile's parent zip. A TMPZ84C015 at 9.8304 MHz (78125/512 board units per T-state); its CTC channel 1 interrupts at about 1010 Hz (vector 0xEA, handler 0x0A05), and the init state machine at Z80 RAM 0xF084 steps once per interrupt. The 93C46 is on port F, pins set CLK first, then DI, then CS (`eeprom_pins_clk_first`, as MAME `io_pf_w`). The gun FPGA reads 0x80 until 0x1400 bytes have been written to it, then serves MAME's `lightgun_data` mux of the four A/D values (`lightgun.h`, the ranges are MAME's ports).
- **The Advanced board's catch-up gap is ten seconds, not four frames** (`MODEL1IO2_CATCHUP_MAX`). Virtua Cop's i960 sits in a delay loop (0x2384-0x2394) for 40-70 frames before it writes "SEGA" to the dual-port RAM (0x1C00034) and waits for the Z80 to clear the flag at 0x1C00040; the Z80 must have run its CTC-paced init in that time. With four frames it lost it, and the handshake came about 100 frames late. Daytona keeps four frames (det-identical).
- **Virtua Cop against MAME**: attract, coin, start, stage select by shooting, play and reload match scene for scene. With `--i960-timing table` its attract countdown (0x50F2BC) reaches 0 at frame 1045 (MAME 1044); with the board timing it runs (`i960_board_timing`, as Daytona), the boot is 47 frames later and the lock-on scene about 90 (i960.md: do not tune it to a game). Sound starts with the attract, at MAME's level. The country is not looked for yet (`REGION_TODO`).
- **The drive board (force feedback) is output only, decoded, not run** (`drive_board.h`, `ffb.h`; Pinboard #1047). Its ROM (epr-16488a) is in no set we load. The game sends one byte at a time through DPRAM 0x11 (i960 `0x01C00022`) and the I/O board's Z80 writes it to the 315-5338A's port E; `model1io.h` keeps the last as `drive`, already savestated. Port E reads 0xFF, so nothing on the board sees the drive board: playing it changes no frame and needs no proto bump. Daytona's sender is ROM 0x1BD5C (the player's car at 0x501220, queue 0x502900, one byte a frame from 0x1C4A8) and repeats a command only when it changes. High nibble = effect, low three bits = strength: 0x1x spring, 0x2x friction (0x27 at rest, fading with speed), 0x3x centring that grows with speed, 0x4x shake (0x42/0x32 alternate on rough ground), 0x5x / 0x6x push one way / the other (contact and crashes; the side is Supermodel's Model 3 convention, the game alone does not tell it), the rest set-up. A pad gets only the pushes and shakes as rumble; a wheel SDL can drive gets all four as haptic effects. Never feed the force back into `io_5649.h`'s simulated wheel: that would change what the i960 reads. Sega Rally's drive board speaks another language (memory-bus.md, the 315-5649).
